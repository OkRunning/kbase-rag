# 文档增量更新与版本治理详细设计方案

## 1. 背景

当前导入链路已经支持 PDF / Markdown 文档解析、图片处理、文档切分、item_name 识别、BGE-M3 embedding 和 Milvus 写入；查询链路已经支持 `tenant_id`、`kb_id`、`doc_id` 等基础 metadata，并在 Milvus 检索时强制拼接租户和知识库过滤条件。

但当前导入节点仍偏“覆盖式导入”：`node_import_milvus` 会按同一租户知识库下的 `item_name` 删除旧向量，再写入新向量。这种方式在单人测试阶段简单有效，但在生产场景会带来几个问题：

- 同一文档重复上传时，即使内容不变，也会重复解析、切分和 embedding。
- 文档更新过程中，如果先删旧向量再写新向量，查询可能短暂读不到资料。
- 文档新旧版本缺少状态记录，无法判断当前线上生效版本。
- chunk、向量和 embedding 模型、切分策略缺少绑定关系，后续升级 embedding 或 chunk 参数时难以灰度和回滚。
- 删除文档后缺少软删除与延迟物理清理机制，容易在“可回滚”和“彻底删除”之间摇摆。
- 查询结果无法稳定追踪到回答基于哪个文档版本、chunk 版本和向量版本。

本方案对应 `RAG_FUTURE_OPTIMIZATION_PLAN.md` 中的 Plan 3：文档增量更新与版本治理，目标是在保持现有 API 和 LangGraph 主流程尽量兼容的前提下，为导入和查询链路补齐文档版本、chunk 版本、向量版本、active 过滤、软删除和回滚能力。

## 2. 设计目标

### 2.1 产品目标

- 支持同一文档的多版本管理。
- 支持重复上传去重，内容未变化时不重复生成 embedding。
- 支持文档更新后只让 active 版本参与线上查询。
- 支持文档软删除，删除后查询不再召回对应内容。
- 支持文档版本回滚，回滚后查询能重新命中旧版本内容。
- 支持查询结果追溯到 `doc_version`、`chunk_hash`、`vector_version` 和 `embedding_model`。

### 2.2 工程目标

- 优先小范围演进，不重写导入和查询主流程。
- 复用现有 `tenant_id`、`kb_id` 隔离模型。
- 复用现有 Milvus shared collection + metadata filter 方案。
- 引入 MongoDB 版本元数据，Milvus 继续承担向量检索。
- 先实现“版本状态过滤 + 增量 embedding + 回滚”，再扩展后台物理清理、diff 页面和发布流水线。
- 与 Plan 1 评测基线结合，每次 chunk 策略或向量版本升级都可量化对比。

### 2.3 非目标

- 不在本阶段实现完整 RBAC 权限系统。
- 不在本阶段实现可视化多版本在线 diff 页面。
- 不在本阶段把 Prompt 和检索策略发布治理合并进来，相关内容由 Plan 4 承接。
- 不强制迁移为“每租户一个 Milvus collection”或“每知识库 partition”。
- 不强制一次性物理删除历史向量，避免破坏回滚窗口。

## 3. 总体架构

### 3.1 核心思路

把文档导入从“覆盖旧数据”调整为“写入新版本、校验完整性、原子切换 active version”。

```text
上传文档
  -> 规范化 tenant_id / kb_id / doc_id
  -> 计算 file_hash / content_hash
  -> 判断是否命中已有 active 版本
  -> 新建 pending 文档版本
  -> 解析 PDF / Markdown
  -> 生成 chunks 和 chunk_hash
  -> 对比上一 active 版本 chunks
  -> 复用未变化 chunk 的向量，新增/变化 chunk 生成 embedding
  -> 写入 Milvus，标记 doc_version / vector_version / status=pending
  -> 完整性校验
  -> Mongo 原子切换 active_version
  -> 将新版本 chunk/vector 标记 active
  -> 将旧版本标记 archived
```

查询侧只检索当前可见版本：

```text
用户查询
  -> Query Understanding
  -> Milvus 检索
       filter:
         tenant_id == 当前租户
         kb_id == 当前知识库
         item_name in [...]
         doc_status == "active"
         chunk_status == "active"
         vector_status == "active"
         vector_version in 当前生效向量版本
  -> RRF / Rerank / Answer
  -> 返回答案和版本来源
```

### 3.2 版本对象关系

```text
tenant
  -> kb
      -> document(doc_id)
          -> document_version(doc_id + doc_version)
              -> chunk(chunk_uid / chunk_hash)
                  -> vector(vector_uid / vector_version)
```

核心原则：

- `doc_id` 表示逻辑文档，例如同一本产品手册。
- `doc_version` 表示逻辑文档的内容版本。
- `chunk_hash` 表示某个切片文本和关键 metadata 的稳定指纹。
- `vector_version` 表示 embedding 模型、chunk 策略和 schema 的组合版本。
- 查询默认只使用 active 文档版本和 active 向量版本。

## 4. 数据模型设计

### 4.1 MongoDB 集合

第一阶段建议新增或约定以下集合：

| 集合 | 作用 |
| --- | --- |
| `rag_documents` | 逻辑文档表，记录当前 active version 和删除状态。 |
| `rag_document_versions` | 文档版本表，记录每次上传、解析和发布状态。 |
| `rag_chunks` | chunk 元数据表，记录 chunk hash、顺序、文本摘要和状态。 |
| `rag_vector_versions` | 向量版本配置表，记录 embedding 模型和 chunk 策略。 |
| `rag_import_jobs` | 导入任务表，记录导入进度、错误和版本切换结果。 |

如果短期不希望新增太多集合，可先实现 `rag_documents`、`rag_document_versions`、`rag_vector_versions` 三个集合；`rag_chunks` 可通过 Milvus metadata 和导入快照补足，后续再独立沉淀。

### 4.2 `rag_documents`

逻辑文档表只保存文档的当前状态和 active 指针。

```json
{
  "_id": "tenant_a:product_manual:doc_001",
  "tenant_id": "tenant_a",
  "kb_id": "product_manual",
  "doc_id": "doc_001",
  "title": "HAK 180 烫金机说明书",
  "source_type": "upload",
  "file_name": "HAK180_manual.pdf",
  "active_version": 3,
  "latest_version": 3,
  "status": "active",
  "deleted_at": null,
  "created_by": "u001",
  "created_at": "2026-07-20T10:00:00+08:00",
  "updated_at": "2026-07-24T10:00:00+08:00"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `_id` | 建议使用 `tenant_id:kb_id:doc_id`，避免跨租户冲突。 |
| `active_version` | 当前查询生效版本。 |
| `latest_version` | 最新上传版本，不一定已经 active。 |
| `status` | `active`、`deleted`、`disabled`。 |
| `deleted_at` | 软删除时间，未删除为空。 |

推荐索引：

```javascript
db.rag_documents.createIndex(
  { tenant_id: 1, kb_id: 1, doc_id: 1 },
  { unique: true }
)
db.rag_documents.createIndex({ tenant_id: 1, kb_id: 1, status: 1 })
```

### 4.3 `rag_document_versions`

文档版本表记录每次上传和处理结果。

```json
{
  "_id": "tenant_a:product_manual:doc_001:3",
  "tenant_id": "tenant_a",
  "kb_id": "product_manual",
  "doc_id": "doc_001",
  "doc_version": 3,
  "status": "active",
  "file_name": "HAK180_manual.pdf",
  "file_hash": "sha256:file_hash",
  "content_hash": "sha256:normalized_markdown_hash",
  "parser": {
    "type": "mineru",
    "version": "default"
  },
  "chunk_strategy": {
    "name": "markdown_heading",
    "version": "v1",
    "chunk_size": null,
    "chunk_overlap": null
  },
  "vector_version": "bge_m3_v1_md_heading_v1",
  "chunk_count": 128,
  "changed_chunk_count": 12,
  "reused_chunk_count": 116,
  "milvus_insert_count": 12,
  "activated_at": "2026-07-24T10:06:00+08:00",
  "created_by": "u001",
  "created_at": "2026-07-24T10:00:00+08:00",
  "updated_at": "2026-07-24T10:06:00+08:00",
  "error": null
}
```

状态枚举：

| 状态 | 含义 | 查询是否可见 |
| --- | --- | --- |
| `pending` | 版本已创建，正在处理。 | 否 |
| `ready` | 处理完成，等待激活。 | 否 |
| `active` | 当前线上生效版本。 | 是 |
| `archived` | 历史版本，可回滚。 | 否 |
| `failed` | 导入失败。 | 否 |
| `deleted` | 已软删除。 | 否 |

推荐索引：

```javascript
db.rag_document_versions.createIndex(
  { tenant_id: 1, kb_id: 1, doc_id: 1, doc_version: 1 },
  { unique: true }
)
db.rag_document_versions.createIndex({ tenant_id: 1, kb_id: 1, status: 1 })
db.rag_document_versions.createIndex({ content_hash: 1 })
```

### 4.4 `rag_chunks`

chunk 元数据表用于增量对比、审计和回滚。Milvus 中仍保存检索所需正文和向量字段。

```json
{
  "_id": "tenant_a:product_manual:doc_001:3:chunk_00042",
  "tenant_id": "tenant_a",
  "kb_id": "product_manual",
  "doc_id": "doc_001",
  "doc_version": 3,
  "chunk_uid": "doc_001_v3_chunk_00042",
  "chunk_index": 42,
  "chunk_hash": "sha256:chunk_hash",
  "content_hash": "sha256:chunk_content_hash",
  "title": "安全注意事项",
  "parent_title": "第 2 章 使用前准备",
  "item_name": "HAK 180 烫金机",
  "content_preview": "使用设备前请确认...",
  "status": "active",
  "source_chunk_uid": "doc_001_v2_chunk_00041",
  "created_at": "2026-07-24T10:04:00+08:00"
}
```

chunk 对比建议以 `chunk_hash` 为主。第一阶段不需要做复杂语义 diff，只判断三类：

| 类型 | 判定方式 | 处理方式 |
| --- | --- | --- |
| `unchanged` | 新旧 `chunk_hash` 相同。 | 复用旧向量或复制 metadata 指向新版本。 |
| `changed` | 同位置或同标题下 hash 不同。 | 重新生成 embedding。 |
| `added` | 新版本出现旧版本没有的 hash。 | 生成 embedding 并写入 Milvus。 |
| `removed` | 旧版本有，新版本没有。 | 标记旧 chunk archived，不参与查询。 |

### 4.5 `rag_vector_versions`

向量版本表记录 embedding 模型、切分策略和 Milvus schema 的组合。

```json
{
  "_id": "tenant_a:product_manual:bge_m3_v1_md_heading_v1",
  "tenant_id": "tenant_a",
  "kb_id": "product_manual",
  "vector_version": "bge_m3_v1_md_heading_v1",
  "status": "active",
  "embedding_model": "bge-m3",
  "embedding_dimension": 1024,
  "embedding_version": "v1",
  "chunk_strategy": "markdown_heading",
  "chunk_strategy_version": "v1",
  "schema_version": "milvus_chunks_v2",
  "dense_weight_default": 0.9,
  "sparse_weight_default": 0.1,
  "created_at": "2026-07-24T10:00:00+08:00",
  "activated_at": "2026-07-24T10:00:00+08:00"
}
```

查询侧通过当前 active `vector_version` 过滤。如果后续需要灰度新 embedding 模型，可以在 Plan 4 的 retrieval profile 中引用不同 `vector_version`。

### 4.6 Milvus metadata 扩展

现有 collection 已启用 `enable_dynamic_field=True`，可先通过动态字段新增版本 metadata，避免第一阶段强制重建 collection。

新增字段建议：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `doc_version` | int | 文档版本号。 |
| `chunk_uid` | string | 业务 chunk 唯一 ID。 |
| `chunk_hash` | string | chunk 指纹。 |
| `chunk_index` | int | chunk 在文档内的顺序。 |
| `chunk_status` | string | `pending`、`active`、`archived`、`deleted`。 |
| `doc_status` | string | 文档状态，查询只允许 active。 |
| `vector_version` | string | 当前向量版本。 |
| `vector_status` | string | `pending`、`active`、`archived`、`deleted`。 |
| `embedding_model` | string | embedding 模型名称。 |
| `embedding_version` | string | embedding 模型版本。 |
| `chunk_strategy` | string | 切分策略名称。 |
| `schema_version` | string | metadata schema 版本。 |

查询输出字段也需要补充这些字段，便于回答引用和观测追踪。

## 5. Hash 与版本号规则

### 5.1 `doc_id`

兼容当前行为：如果用户不传 `doc_id`，仍使用 `task_id`。生产建议前端或调用方传稳定 `doc_id`，否则每次上传都会被视为新文档。

推荐 doc_id 生成方式：

```text
tenant_id + kb_id + source_path/file_name/business_key -> slug/hash
```

### 5.2 `doc_version`

同一 `tenant_id + kb_id + doc_id` 下单调递增，从 1 开始。

创建新版本时：

1. 读取 `rag_documents.latest_version`。
2. 新版本号等于 `latest_version + 1`。
3. 先写 `rag_document_versions.status=pending`。
4. 处理成功后再更新 active 指针。

### 5.3 `file_hash`

对原始上传文件二进制内容计算 SHA-256。适用于判断上传文件是否完全一致。

### 5.4 `content_hash`

对解析后的规范化 Markdown 文本计算 SHA-256。适用于判断 PDF 文件元信息变化但正文未变化的场景。

规范化建议：

- 统一换行符为 `\n`。
- 去除行尾空格。
- 压缩连续空行为最多两个。
- 保留标题、表格和列表结构。
- 不删除中文标点，避免破坏业务语义。

### 5.5 `chunk_hash`

对 chunk 关键内容计算 SHA-256。

建议输入：

```text
schema_version
chunk_strategy
item_name
title
parent_title
normalized_content
```

这样可以避免只有正文相同但标题上下文不同的 chunk 被误判为同一块。

### 5.6 `vector_version`

建议采用可读版本字符串：

```text
{embedding_model}_{embedding_version}_{chunk_strategy}_{chunk_strategy_version}
```

示例：

```text
bge_m3_v1_md_heading_v1
```

## 6. 导入链路详细设计

### 6.1 LangGraph 节点调整

当前链路：

```text
node_entry
  -> node_pdf_to_md / node_md_img
  -> node_document_split
  -> node_item_name_recognition
  -> node_bge_embedding
  -> node_import_milvus
```

目标链路：

```text
node_entry
  -> node_document_version_prepare
  -> node_pdf_to_md / node_md_img
  -> node_document_split
  -> node_chunk_diff
  -> node_item_name_recognition
  -> node_bge_embedding
  -> node_import_milvus
  -> node_document_version_activate
```

第一阶段可少加节点，保持改动更小：

| 阶段 | 节点 | 做法 |
| --- | --- | --- |
| P1-A | `node_document_version_prepare` | 新增节点，创建 pending 版本并判断是否跳过。 |
| P1-A | `node_import_milvus` | 改为不删除旧 active 数据，写入 pending/active metadata。 |
| P1-A | `node_document_version_activate` | 新增节点，处理完成后切换 active。 |
| P1-B | `node_chunk_diff` | 新增节点，实现 chunk hash 对比和 embedding 复用。 |

如果想更保守，也可以先把 prepare / activate 写入 `node_entry` 和 `node_import_milvus`，但长期建议拆节点，让版本治理逻辑更清晰。

### 6.2 State 扩展

`ImportGraphState` 建议新增：

```python
doc_version: int
previous_doc_version: int | None
file_hash: str
content_hash: str
vector_version: str
chunk_strategy: str
chunk_strategy_version: str
import_action: str
skip_reason: str
changed_chunks: list
reused_chunks: list
removed_chunks: list
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `doc_version` | 当前导入生成的新版本号。 |
| `previous_doc_version` | 上一个 active 版本，用于 diff 和回滚。 |
| `import_action` | `create`、`update`、`noop`、`rollback`、`delete`。 |
| `skip_reason` | 内容无变化时记录跳过原因。 |
| `changed_chunks` | 新增或变化的 chunk，需要 embedding。 |
| `reused_chunks` | 可复用向量的 chunk。 |
| `removed_chunks` | 新版本删除的旧 chunk。 |

### 6.3 准备版本

`node_document_version_prepare` 负责：

1. 规范化 `tenant_id`、`kb_id`、`doc_id`。
2. 计算上传文件的 `file_hash`。
3. 查询 `rag_documents` 当前 active 信息。
4. 如果 `file_hash` 与 active 版本一致，设置 `import_action=noop`，后续路由直接 END。
5. 否则创建 `rag_document_versions.status=pending`。
6. 将 `doc_version`、`previous_doc_version` 写入 State。

注意：对于 PDF，`content_hash` 必须在解析完成后计算，因此 prepare 阶段只能用 `file_hash` 做快速跳过。解析完成后如果 `content_hash` 未变化，也可以跳过后续 chunk 和 embedding，并把版本记录为 `noop` 或 `archived_duplicate`。

### 6.4 解析与内容 hash

PDF 转 Markdown 或 Markdown 图片处理完成后，对 `state["md_content"]` 或 `state["md_path"]` 读取出的规范化文本计算 `content_hash`。

处理策略：

| 场景 | 处理 |
| --- | --- |
| `file_hash` 相同 | 直接 noop，不进入解析。 |
| `file_hash` 不同但 `content_hash` 相同 | 记录新上传文件，但不重新 embedding，不切 active 或创建等价版本。 |
| `content_hash` 不同 | 继续 chunk diff 和 embedding。 |

### 6.5 Chunk diff

`node_chunk_diff` 负责将新版本 chunks 与上一 active 版本 chunks 对比。

第一阶段推荐简单 hash diff：

1. 为新版本每个 chunk 生成 `chunk_hash`。
2. 查询上一 active 版本的 `rag_chunks` 或 Milvus metadata。
3. 如果 `chunk_hash` 在旧版本存在，标记 `reused`。
4. 如果不存在，标记 `changed`。
5. 旧版本中未出现在新版本的 chunk 标记 `removed`。

复杂逻辑需要中文注释，重点解释为什么不能按 `chunk_index` 单独判断：章节插入会导致后续 index 全部偏移，但内容 hash 仍能稳定识别未变化片段。

### 6.6 增量 embedding

`node_bge_embedding` 调整为只对 `changed_chunks` 生成 embedding。

处理方式：

- `changed` / `added` chunk：调用 `generate_embeddings`。
- `reused` chunk：第一阶段可重新写一条新版本 metadata，但复用旧向量值；如果读取旧向量成本较高，也可先不复制，查询时允许 `doc_version=active_version` 的完整新向量集合，P1-B 再优化复用。
- embedding 结果必须写入 `embedding_model`、`embedding_version`、`vector_version`。

为了减少改动，建议 P1-A 先实现“内容未变整文档跳过 + 新版本全量 embedding + active 切换”；P1-B 再做 chunk 级增量 embedding。这样能先解决旧向量污染和回滚，再优化成本。

### 6.7 Milvus 写入

`node_import_milvus` 调整原则：

- 不再按 `item_name` 删除旧数据。
- 写入新版本向量时附带完整版本 metadata。
- 初始写入状态可以是 `vector_status=pending`。
- 版本激活成功后，将新版本向量标记为 `active`，旧版本向量标记为 `archived`。

Milvus update 能力在不同部署和 SDK 版本中可用性不同，建议实现两种策略：

| 策略 | 说明 | 优先级 |
| --- | --- | --- |
| 插入即 active | 先写 Mongo pending，Milvus 写入直接 `active`，查询侧同时依赖 `rag_documents.active_version` 构造 filter。 | P1 推荐 |
| pending 后 activate | Milvus 写 `pending`，激活时 update 状态为 `active`。 | P2 完善 |

P1 推荐使用“插入即 active + 查询按 Mongo active_version 过滤”。因为只要 Mongo active 指针未切换，查询不会检索新版本；切换后才会命中新版本。旧版本无需立即更新 Milvus 状态，只要查询过滤 `doc_version == active_version` 即可避免污染。

### 6.8 激活版本

`node_document_version_activate` 负责完成原子切换：

1. 校验新版本 Milvus 写入数量与 chunk 数量匹配。
2. 更新 `rag_document_versions`：新版本 `status=active`。
3. 更新旧版本 `status=archived`。
4. 更新 `rag_documents.active_version=new_version`、`latest_version=new_version`。
5. 记录 `document.version_activated` 事件。

MongoDB 建议使用事务；如果当前部署没有副本集或事务能力，则使用带条件的单文档更新保障一致性：

```javascript
db.rag_documents.updateOne(
  {
    tenant_id,
    kb_id,
    doc_id,
    active_version: previous_doc_version
  },
  {
    $set: {
      active_version: new_doc_version,
      latest_version: new_doc_version,
      updated_at: now
    }
  }
)
```

如果 matched_count 为 0，说明期间有其他导入抢先切换，需要将当前版本标记为 `failed_conflict` 或 `ready`，等待人工处理。

## 7. 查询链路详细设计

### 7.1 查询过滤条件

当前过滤条件：

```text
tenant_id == ... and kb_id == ... and item_name in [...]
```

目标过滤条件：

```text
tenant_id == ...
and kb_id == ...
and item_name in [...]
and doc_status == "active"
and chunk_status == "active"
and vector_status == "active"
and vector_version in [...]
```

如果采用 P1 推荐方案，查询节点需要先查询 Mongo 中当前 active 文档版本，构造更具体的 filter：

```text
tenant_id == ...
and kb_id == ...
and item_name in [...]
and (
  (doc_id == "doc_001" and doc_version == 3)
  or (doc_id == "doc_002" and doc_version == 1)
)
and vector_version == "bge_m3_v1_md_heading_v1"
```

第一阶段推荐采用 `doc_id/doc_version` active map 方案：查询前从 Mongo 读取当前 active 指针，再把 active 版本写入 Milvus filter。这样即使 Milvus 暂时不支持稳定 update 旧向量状态，也不会把未激活版本或旧版本召回。等后续确认 Milvus metadata update 能力可靠后，再切换为更短的 `metadata_status` filter。

### 7.2 Active 版本解析

新增工具函数建议放在 `app/core/document_version.py` 或 `app/clients/document_version_store.py`：

```python
def get_active_document_versions(tenant_id: str, kb_id: str, doc_ids: list[str] | None = None) -> dict[str, int]:
    """查询当前知识库内文档 active 版本。"""
```

查询节点调用点：

- `node_search_embedding.py`
- `node_search_embedding_hyde.py`
- 后续如 BM25 / KG 检索也需要复用。

### 7.3 输出字段

Milvus `output_fields` 建议补充：

```text
doc_version
chunk_uid
chunk_hash
chunk_index
chunk_status
vector_version
vector_status
embedding_model
embedding_version
```

这些字段会进入：

- RRF / Rerank 中间结果。
- 节点快照。
- 事件时间线。
- Answer 输出引用。
- Plan 1 评测报告。

### 7.4 回答引用

答案引用建议保留版本字段：

```json
{
  "doc_id": "doc_001",
  "doc_version": 3,
  "chunk_uid": "doc_001_v3_chunk_00042",
  "chunk_hash": "sha256:chunk_hash",
  "file_title": "HAK180_manual.pdf",
  "title": "安全注意事项",
  "vector_version": "bge_m3_v1_md_heading_v1"
}
```

这样当用户质疑答案来源时，可以追溯到准确版本，而不是只知道来自某个文件标题。

## 8. 删除与回滚设计

### 8.1 文档软删除

删除接口只做逻辑删除：

1. 更新 `rag_documents.status=deleted`、`deleted_at=now`。
2. 更新当前 active 版本 `status=deleted`。
3. Milvus 可选 update `doc_status=deleted`。
4. 查询侧过滤 `status=active`，因此删除后立即不可见。
5. 记录 `document.deleted` 事件。

不建议 API 请求内执行 Milvus 物理删除，避免长耗时和不可回滚。

### 8.2 延迟物理清理

后台清理任务处理：

- 已 `deleted` 超过保留期的文档。
- 已 `archived` 且超过回滚窗口的旧版本。
- `failed` / `pending` 超时的半成品向量。

默认保留期建议：

| 对象 | 保留期 |
| --- | --- |
| archived 文档版本 | 30 天 |
| deleted 文档版本 | 7-30 天，按业务合规要求调整 |
| failed pending 向量 | 1-7 天 |
| 导入 job 明细 | 90 天 |

### 8.3 回滚

回滚只切 active 指针，不重新 embedding：

```text
POST /kb/{kb_id}/documents/{doc_id}/rollback
  body: { "target_version": 2 }
```

流程：

1. 校验目标版本属于同一 `tenant_id + kb_id + doc_id`。
2. 校验目标版本状态为 `archived` 或 `active`。
3. 校验目标版本向量仍存在，且 `vector_version` 与当前查询配置兼容。
4. 将当前 active 版本标记为 `archived`。
5. 将目标版本标记为 `active`。
6. 更新 `rag_documents.active_version=target_version`。
7. 记录 `document.version_rolled_back` 事件。

如果目标版本的向量已被物理清理，应拒绝回滚并返回明确错误。

## 16. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 更新过程中读到半成品数据 | 查询结果缺失或混入新旧版本。 | 先写新版本，再切 active；查询只看 active。 |
| Milvus metadata update 能力受限 | 无法直接修改旧向量状态。 | 查询使用 `doc_version` active map 过滤；后续异步清理。 |
| 并发上传同一 doc_id | active_version 被覆盖或错乱。 | Mongo 条件更新或事务，失败版本进入 `failed_conflict`。 |
| chunk 策略变化导致 hash 大面积变化 | 增量复用率下降。 | 将 `chunk_strategy_version` 纳入 `vector_version`，用评测判断收益。 |
| 查询 filter 过长 | Milvus 检索性能下降。 | P1 用 status 字段过滤，P2 再优化 active map 缓存或 partition。 |
| 历史数据缺少版本字段 | 上线后旧知识库不可查。 | 先兼容 legacy，再迁移补字段或重新导入。 |
| 软删除保留期不符合法规 | 数据合规风险。 | 按知识库配置 retention，必要时提供立即物理删除审批流程。 |

## 17. 验收标准

- 同一文档重复上传且内容未变化时，不重复生成 embedding，并返回 skipped 状态。
- 文档更新成功后，查询只命中新版本 active chunk。
- 文档更新失败时，旧 active 版本仍可查询。
- 文档删除后，查询结果中不再出现该文档内容。
- 文档可回滚到上一版本，且查询结果同步回到上一版本内容。
- 每条查询引用都能追踪到 `tenant_id`、`kb_id`、`doc_id`、`doc_version`、`chunk_uid`、`chunk_hash` 和 `vector_version`。
- 版本切换、删除、回滚都有事件记录和可观测指标。
- 历史默认知识库在迁移期仍保持可查询。

## 18. 推荐落地顺序

建议先做 P1-A，不急着一步到位做 chunk 级增量。原因是版本治理的首要风险不是 embedding 成本，而是线上查询不能混入旧数据、半成品数据和已删除数据。

落地顺序：

1. 新增 Mongo 文档版本模型。
2. 导入链路写入 `doc_version` 和 `vector_version`。
3. 查询链路增加 active 过滤。
4. 实现重复上传 noop。
5. 实现删除和回滚。
6. 补齐测试和观测事件。
7. 再推进 chunk 级 diff 与增量 embedding。

完成 P1-A 后，Plan 3 就具备生产可用的最小闭环；完成 P1-B 后，大文档更新成本会明显下降；完成 P2 后，embedding 模型和 chunk 策略升级可以进入可评测、可灰度、可回滚的治理状态。

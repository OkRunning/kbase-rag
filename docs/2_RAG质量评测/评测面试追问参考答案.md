> 本文配合 `reports/evaluation/eval_dashboard.md` 一起看，每条都给出"话术 + 代码依据 + 进阶追问"，用于面试自我演练。

## A. 评测指标设计类

### A1. 为什么用 Recall@K / Hit@K / MRR@K，三者各自适用什么场景？为什么同时要三个？

**参考答案：**
- Recall@K 回答"该找的证据找回来多少"，衡量召回完整性，当下游 LLM 的上下文窗口有限时，漏召回就是硬伤，所以它是"上限指标"。
- Hit@K 回答"有没有至少命中一条"，是个布尔型，更适合做粗筛门禁，工程上廉价、可解释，用来卡"完全没命中目标证据"的系统性退化。
- MRR@K 回答"第一条正确证据排第几名"，衡量排序质量；RAG 里把对的证据排得越靠前，LLM 越容易用上，下游答案质量对排序很敏感。
- 三个一起用是因为它们各自只描述一个侧面：Recall 高但 MRR 低（证据排到 Top5 末尾）依然体验差；Hit 高但 MRR 低意味着只是恰好命中最后一位；Recall 高 + Hit 高但 MRR 低，说明 rerank 没把对的证据往前提，rerank 模块的收益就需要被质疑。

**代码依据：** `app/evaluation/metrics.py` 中 `recall_at_k` / `hit_at_k` / `mrr_at_k` 三个函数分别实现，并分别在"检索段"和"rerank 段"各算一遍（`evaluate_case_result`），形成 6 个检索类指标。

**进阶追问：** "你怎么定义'一个 chunk 是正确证据'？"
- 答：评测集里每个样本人工标注 `expected_chunk_ids`，匹配方式是 chunk_id 精确比对。人工标注成本高的应对：先从线上 bad case 沉淀一批"金标样本"作为种子集，再通过 LLM 辅助生成候选证据，人工只做审核，不纯靠人工标。

### A2. 答案质量你只用了关键词规则，为什么没用 RAGAS / LLM-as-Judge？什么时候要补？

**参考答案：**
- 关键词规则（`required_keywords_pass` / `required_keywords_coverage` / `forbidden_keywords_pass`）是"确定性的硬门禁"，零成本、零误差、可在 CI 阻断合并，适合做回归基线和禁止词兜底。
- 但它有两个盲区：第一，无法衡量"语义正确性"，答案换一种说法但意思对的情况会被误判为 fail；第二，无法测"忠实度"——答案看起来合规但是编造的，关键词照样能命中。
- 所以补充的顺序是：先用关键词规则稳住回归基线，再在关键 query_type（如 procedure / factual）上叠加 LLM-as-Judge 做 Faithfulness（答案是否被证据支持）和 Answer Relevancy（答案是否切题）。RAGAS 的 Faithfulness 适合填补 `has_local_citation` 抓不到的"证据支持结论"那一层。

**代码依据：** `app/evaluation/metrics.py:163` 的 `has_local_citation` 实际只判断 `reranked_chunk_ids` 是否非空，并不校验"证据真的支撑了答案"。这是关键词规则的典型盲区。

**进阶追问：** "RAGAS 跑出来分数抖动很大怎么办？"
- 答：LLM-as-Judge 有抖动，对策是固定 judge 模型、降低温度、对同一案本跑多次取众数，或用 pairwise comparison（A/B 对比两个 prompt 版本谁更好）替代点估，更稳；同时保留关键词规则做硬门禁，LLM 指标只做辅助参考。

### A3. 把检索和 rerank 两段分别打分，业务上最终看哪段？rerank 没提升甚至拉低 recall 时怎么决策？

**参考答案：**
- 业务最终看 rerank 段，因为它才是喂给 LLM 的最终上下文。但体检要看两段，因为我们想知道 rerank 是不是"物有所值"。
- 比较 `retrieval_recall_at_5` 和 `recall_at_5`、`retrieval_mrr_at_5` 和 `mrr_at_5` 的 delta 就能看出 rerank 的净收益：
  - 若 rerank 后 recall 与检索段持平、MRR 上升 → rerank 在做"把对的往前提"，是有收益的。
  - 若 rerank 后 recall 反而下降 → rerank 把证据挤出 TopK 了，要么调 rerank 的 top_k 留存量，要么换 rerank 模型，要么对低质召回走"rerank 前先扩召回"的策略。
- 决策阈值我倾向：rerank 后 recall 不得低于 retrieval_recall 的 95%，否则视为 rerank 破坏召回，直接回滚 rerank 配置。

**代码依据：** `evaluate_case_result` 同时接受 `retrieved_chunk_ids` 和 `reranked_chunk_ids` 两个列表，对两段分别算 recall/hit/mrr。`eval_dashboard.md` 第七节里 prompt_v2 的案例 `retrieval_recall_at_5=0.5 → recall_at_5=0.5`，且 rerank 后没改善，正是这种"rerank 无收益"的典型。

**进阶追问：** "rerank 模型很贵，怎么评估它的 ROI？"
- 答：用 rerank 段相对检索段的 MRR 提升量 vs rerank 平均耗时/P95 延迟做权衡；MRR 提升越多、答案引用越靠前，ROI 越高；若 MRR 提升小且 latency 多 100ms+，可对低难度 query_type 关掉 rerank 做降本。

### A4. pass_rate 把多个异质指标用阈值卡死再 AND 起来，会不会太"脆"？

**参考答案：**
- 确实偏脆，本质是用"硬 AND"做单点门禁，所以会有"一条样本因一个关键词没命中而整体 fail"的情况。这在当前评测集只有 1 条时尤其明显（看 dashboard 里 pass_rate 在 0 和 1 之间跳）。
- 对策有三条：第一是分层判定，把"硬阻断指标"（hit_at_5=0、forbidden_keywords=0）和"软趋势指标"（关键词覆盖率、MRR）分开，前者直接阻断，后者只记录和回归对比；第二是要求评测集扩到一定规模后才启用 pass_rate 门禁，规模太小时改用"逐案 failed_cases 列表人工 review"；第三是把单条 pass 改成"指标加权分"而不是全 AND，避免一个噪声样本拖垮整体。
- 我倾向的演进：pass_rate 只做"整体趋势看板"，CI 阻断用"任一硬指标在全集均值低于阈值"才阻断，而不是逐案 AND。

**代码依据：** `app/evaluation/schemas.py` 的 `EvalResult.passed()` 用 `hit_score / required_keywords_pass / forbidden_keywords_pass / has_answer` 全部 ≥ 1.0 才返回 True，是硬 AND；`thresholds.py` 的 `evaluate_thresholds` 则是看均值是否过线，是软门禁——两套并存其实就是为了缓解这个脆性。

## B. 工程闭环 / CI 类

### B1. 评测集规模多大？跑一次多久？怎么做采样、分层、回归子集？

**参考答案：**
- 当前评测集 33 条（`data/eval/rag_cases.jsonl`），还有一条临时集（`rag_cases2.jsonl`），属于种子集阶段。跑评会真实调用生产 LangGraph 全链路，每条约几秒到十几秒（含 LLM 调用），目前分钟级可完成。
- 采样策略：
  - **冒烟集**：取 3~5 条覆盖典型 query_type，每次 PR 必跑，秒级反馈。
  - **回归子集**：每个 query_type 取 5 条，CI 跑一次几分钟，用来挡明显回归。
  - **全量集**： nightly 跑，用作版本化基线。
- 分层：样本带 `query_type` 和 `difficulty`，报告按桶报指标，便于看"是不是某一类问题拖后腿"。

**进阶追问：** "评测集会不会退化成刷分？"
- 答：风险在于评测集固定后 prompt/模型可能过拟合到这几条。对策：线上 bad case 持续回流进评测集，并定期留出 hold-out 集（不参与日常迭代），按月用 hold-out 做盲测校验泛化性。

---

### B2. 阈值门禁在 CI 里阻断合并，有没有误杀经验？阈值怎么定才不僵？

**参考答案：**
- 当前阈值（`thresholds.default.json`：pass_rate 0.8 / hit 0.8 / recall 0.8 / mrr 0.5 / 禁止词 1.0）是基于早期种子集定的，在评测集只有几条时确实容易误杀——单条样本失败 pass_rate 直接归零就触发违规（dashboard 第 6 节里 gate_test / threshold_test 都是 pass=0 就触发）。
- 阈值设定原则：
  1. 硬指标（forbidden、hit=0）可以定高（1.0 / 0.8），因为它们反映系统能不能答对。
  2. 软指标（MRR、关键词覆盖率）定中间档（0.5 / 0.9），允许波动。
  3. 评测集扩到几十条以后，阈值要基于"近 N 次 baseline 的均值 - 1 倍标准差"动态滚动，而不是 forever 固定值，这样既能挡回归又不僵。
- 我会接 CI 的方式：默认非阻断，只出报告；只有 `--fail-on-threshold` 才阻断，且首次引入新指标时只告警不阻断，稳定后再升级为阻断。

**代码依据：** `app/evaluation/run_rag_eval.py` 默认 `fail_on_threshold=False`，只有显式传参才退出码 2，符合"先观测后阻断"的渐进策略。

---

### B3. baseline 对比的 delta 多少算回归？有没有"指标涨了但体验差了"的反例？

**参考答案：**
- delta 判回归我分两档：硬指标 delta < 0 即判回归（哪怕只降 0.05，因为它不该降）；软指标 delta 超过 1 倍历史标准差才算回归。同时要求 delta 持续 2 次报告都为负才阻断，避免单次抖动误杀。
- "指标涨了但体验差"的反例确实存在：
  - 关键词覆盖率涨了，但答案变得啰嗦、复读证据，体验反而差——所以还要看答案长度分布、人工满意度。
  - MRR 涨了是把"一个错证据"排到前面碰巧命中关键词，但语义其实错了——所以 MRR 还要配合答案层指标一起看，不能只看检索段。
- 对策：每个版本做一次人工抽样 review（5~10 条），用 LLM-as-Judge 做语义评分，避免指标单维度优化导致"刷分"。

### B4. Langfuse 上报失败降级本地，降级路径里"本地结果可信"的边界在哪？

**参考答案：**
- 降级只影响"可视化和远程追溯",不影响本地指标计算——指标都是在本地用 `metrics.py` 算的，Langfuse 只是把 trace/score 上报做展示（`langfuse_eval.py` 注释明确说"Langfuse 只是评测展示层，失败不应阻断本地质量基线生成"）。
- 降级边界：本地指标照样可信，但失去了 Langfuse 里的逐案 trace 链路和远程历史趋势；所以降级发生时，日志告警 + 强制本地报告归档，事后人工补回 Langfuse。
- 真正不可信的边界是：如果 Langfuse 类的远程观测挂了，而且本地恰好也没写 JSON 报告，那就完全失明——所以双写（本地 JSON + Langfuse）是必须的。

**代码依据：** `app/evaluation/langfuse_eval.py` 的 `eval_trace` 和 `score_result` 都用 try/except 包裹，失败时只 warning 并 yield None，不抛异常；`run_rag_eval.py` 最后 `write_reports` 一定写本地文件。

## C. 答案质量 / 幻觉相关

### C1. 你这套能抓到"回答看起来对但编造细节"的幻觉吗？关键词规则够不够？

**参考答案：**
- 单靠关键词规则抓不到。`required_keywords_pass` 只能验证"应出现的词出现了"，但编造的细节如果恰好包含这些关键词，照样 pass。这是当前评测体系的明确盲区。
- dashboard 第七节里写过：gate_test 的样本检索三指标全 0、但 `has_local_citation=1`、关键词也 pass——这就是典型的"无证据幻觉"，因为 `has_local_citation` 只判断 `reranked_chunk_ids` 非空，不验证证据是否真的支持答案所述结论。
- 解决方案：
  - 加 Faithfulness 指标（RAGAS 或 LLM-as-Judge）：用 judge LLM 逐句拆答案，校验每句是否能在证据里找到支撑，得到一个 [0,1] 忠实度。
  - 加引用抽取校验：让答案显式标注每个论断的来源 chunk_id，再 match 证据内容，做句子级对齐。
  - 把"检索段没有命中目标 chunk 但答案仍含必选词"直接标红为高风险样本，进入人工 review 队列。

**代码依据：** `app/evaluation/metrics.py:163` 的 `has_local_citation = 1.0 if reranked_chunk_ids else 0.0`，是"有没有证据"而非"证据是否被用上"。`eval_dashboard.md` 第七节第三点是真实样本佐证。

---

### C2. `has_local_citation` 证明"引用了证据"，但"证据支持这个结论"怎么验？

**参考答案：**
- 现状只能验"列表非空"，不能验"内容对齐"。要验"证据支持结论"需要句子级 entailment：
  - 把答案拆成原子论断（每一条陈述），对每条论断去 reranked_chunk 内容里找 entailment 关系（用一个小判别模型或 LLM-as-Judge 做 NLI）。
  - 一个论断找不到支撑 → 幻觉，用 Faithfulness = 被支撑论断数 / 总论断数。
- 工程实现建议：先在 procedure / factual 这种高幻觉代价的 query_type 上试点，避免对全部样本跑 entailment 太贵；只对"答案长度 > 阈值 且 检索 hit=0"的高风险子集自动触发。

**进阶追问：** "entailment 模型本身也会错，怎么办？"
- 答：判别模型错检分两种——把真幻觉判成 OK（漏报）和把正确论断判成幻觉（误报）。前者用更严阈值 + 人工 review 兜底，后者成本高用低阈值 + 给人工标注机会；优先级上宁可误报也不要漏报，因为漏报就是幻觉上线。

---

### C3. 禁止词规则怎么维护？硬编码还是从 bad case 沉淀？

**参考答案：**
- 现在是按样本硬编码 `forbidden_keywords`，适合兜底常见雷区（"无法确定 / 请联系销售"这类不应出现在答案里的退避话术）。
- 演进路径：
  - 从线上 bad case 抽取：把用户点踩的答案做关键词挖掘，高频出现的"敷衍词 / 推脱话"沉淀进禁止词词表。
  - 区分"全样本禁止词"和"特定 query_type 禁止词"：前者全局阻断（如"我不知道"），后者按类型阻断（如 procedure 类禁止出现"参考官方文档"这种不解决问题的话术）。
- 风险点：禁止词不能用太多，否则会过拟合到个别 bad case，把正常回答也误杀。要定期回扫，淘汰只对个例有效的禁止词。

---

### C4. 多语言、长答案、答案分点列举时，关键词匹配会不会失效？

**参考答案：**
- 会失效：
  - 多语言：`keyword in answer` 是字符级匹配，答案做了中英混排、近义改写就跳过匹配，需要加同义词/同义改写展开，或干脆改成语义相似度匹配。
  - 长答案：关键词覆盖率高但答案冗长废话多，coverage 指标失真，要约束答案长度或用答案信息密度做补充。
  - 分点列举：分点格式（1./2./-）可能把关键词拆开，纯子串匹配漏命中，需要先做答案分块再匹配，或用 regex 允许中间有分隔符。
- 对策：关键词规则只做硬门禁的兜底指标，真正的答案质量应交由 LLM-as-Judge + Faithfulness，关键词只用来"防止答案完全不提核心概念"这个最低线。

## D. 产品 / 数据策略类

### D1. 评测集怎么持续扩充？bad case → 评测样本的回流闭环建了没有？

**参考答案：**
- 现在主要是人工种子集（33 条），回流闭环还在建。
- 设计好的链路：线上用户点踩/负反馈 → 落入 bad case 池 → 人工审核/AI 辅助改写成标准评测样本（补 expected_chunk_ids / required_keywords）→ 进入评测集 → 下次评测自动覆盖。
- 关键点：
  - 回流时必须把当时的 session 上下文（query、最终召回 chunk、答案、rerank 排序）一起冻结，否则事后无法复现。
  - 评测集版本化：每个 bad case 进集时打 `metadata.added_date` 和 `source: bad_case`，方便区分种子集和线上回流集，做细分报告。

---

### D2. 对错样本（rewrite / 改 prompt）修复后，怎么确认"治好了这条没弄坏别的"？回归子集怎么选？

**参考答案：**
- 不能只跑这条，必须配跑一个"相邻样本回归子集"——同一 query_type、相邻 difficulty 的 5~10 条作为邻居集一起跑，看 fix 没有把邻居样本指标带崩。
- 工程做法：每次改 prompt/rerank 参数，跑 fix 样本 + 该 query_type 的回归子集 + 1 条冒烟样本，三层结果合并判定。
- 阈值：fix 样本要 turn fail→pass；回归子集允许单条波动但均值不降；冒烟样本必须 pass。
- 对"改 prompt 帮了 grep 类型但伤了 procedure 类型"的跨桶退化，要靠 query_type 分层报告直接暴露，不能只看全集均值。

---

### D3. query_type / difficulty 标签怎么用？有没有做"难例分析"驱动迭代优先级？

**参考答案：**
- 样本带 `query_type`（procedure/factual/realtime/unknown 等）和 `difficulty`，当前用于报告分桶和检索计划路由（`node_retrieval_gate` 用 query_type 决定是否触发 web_fallback）。
- 难例分析用法：
  - 报告按 query_type 分桶看 pass_rate，找出最差桶作为下个迭代重点（比如 procedure 桶差就优先修流程类）。
  - 按 difficulty 分桶看"哪类是当前系统天花板"，难例通过率低 → 优先扩证据 / 补 rerank；易例通过率低 → 系统性问题，先修流程。
- 沉淀：把难例转化为"难例回归子集"，每次迭代必跑，专项 tracking。

---

## E. 应该准备的数字（强烈建议补全）

面试官一旦问"有什么数字证明这套在工作"，要有数据回答：

- 评测集规模：33 条种子 + 持续扩充中（按 query_type 5~6 桶）。
- 历史报告份数：12 份，覆盖 6 种 profile（baseline / prompt_v2 / gate_test / threshold_test / smoke_test / manual_label_test）。
- 已发现的真实问题案例：
  - prompt_v2 在 recall_at_5 上相对 baseline delta -0.50，门禁已触发阈值违规（current 0.50 < threshold 0.80），验证门禁对真实回归有效。

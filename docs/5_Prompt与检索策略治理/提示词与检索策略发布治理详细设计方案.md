# 提示词与检索策略发布治理详细设计方案

## 1. 背景

当前查询链路已经具备 Query Understanding、商品名确认、普通向量检索、HyDE 检索、Web Search、RRF、Rerank 和 Answer Generation 等能力；Prompt 通过 `app/core/load_prompt.py` 从 `prompts/*.prompt` 文件加载，检索参数主要散落在各查询节点和配置模块中。

这种方式适合开发阶段快速迭代，但进入生产治理后会遇到以下问题：

- Prompt 文件改动需要随代码一起发布，无法做到运行时切换。
- 每次回答使用了哪个 Prompt、模型参数和检索策略缺少统一追踪。
- Prompt、HyDE、RRF、Rerank、Evidence Gate 参数调整后，缺少版本化对比和灰度能力。
- 不同租户、知识库、问题类型可能需要不同 Prompt 和检索策略，但当前缺少匹配规则。
- 发现线上效果退化时，只能回滚代码或手工恢复文件，回滚路径慢且不可观测。
- 检索参数如果零散覆盖，会造成“线上到底用了哪套策略”难以解释。

本方案对应 `RAG_FUTURE_OPTIMIZATION_PLAN.md` 中的 Plan 4：Prompt 与检索策略发布治理，目标是在不重写现有 LangGraph 查询主流程的前提下，将 Prompt、模型参数和检索参数演进为可版本化、可评测、可灰度、可回滚的发布配置。

## 2. 设计目标

### 2.1 产品目标

- 支持不修改代码即可切换回答 Prompt、HyDE Prompt、Query Understanding Prompt 等核心提示词版本。
- 支持不同 `tenant_id`、`kb_id`、`query_type` 使用不同 Prompt 和检索策略。
- 支持新版本按租户、知识库、问题类型、用户白名单或百分比灰度。
- 支持发布前绑定 RAG 质量评测报告，保留发布依据。
- 支持发现退化后快速回滚到上一 active 版本。
- 每次回答都能追踪命中的 Prompt 版本、模型参数、retrieval profile 和匹配原因。

### 2.2 工程目标

- 优先小范围演进，不改变现有查询 API 的必填字段。
- 保留 `prompts/*.prompt` 文件和当前默认检索参数作为 fallback，保证旧调用兼容。
- 复用现有 MongoDB 保存治理元数据，Milvus 仍只承担向量检索。
- 在 LangGraph 查询 State 中增加配置快照字段，让后续节点只消费本次请求已解析好的配置。
- 将检索参数作为 `retrieval_profile` 整体版本治理，避免按请求零散覆盖。
- 与 Plan 1 评测基线结合，让 Prompt 或检索策略发布前后可以量化对比。
- 所有新增指标遵循低基数标签原则，不把 `tenant_id`、`kb_id`、`version_id` 直接作为 Prometheus label。

### 2.3 非目标

- 不在本阶段实现可视化 Prompt 编辑器。
- 不在本阶段实现完整审批工作流。
- 不在本阶段实现自动发布门禁，只保留评测报告绑定和人工判断入口。
- 不在本阶段重构全部查询节点，只增加配置解析层和必要的参数读取点。
- 不允许业务查询请求随意传入任意 Prompt 内容，避免绕过版本治理和审计。

## 3. 总体架构

### 3.1 核心思路

新增一层“查询配置解析”能力，在查询进入多路召回前，根据请求 scope 和 query_type 解析本次应使用的 Prompt 版本、模型参数、检索策略和匹配原因，并写入 LangGraph State。

```text
用户查询
  -> 初始化 QueryGraphState
  -> Query Understanding / 商品名确认
  -> 解析 Query Config Snapshot
       - tenant_id
       - kb_id
       - user_id
       - query_type
       - stable request hash
       - prompt bindings
       - retrieval profile
       - model params
       - match reasons
  -> 普通向量检索
  -> HyDE 检索
  -> Web Search
  -> RRF
  -> Rerank
  -> Answer Generation
  -> 记录 prompt_version / retrieval_profile / eval_report_id / match_reason
```

发布治理侧提供管理接口：

```text
创建草稿
  -> 运行离线评测
  -> 绑定评测报告
  -> 配置灰度规则
  -> 激活灰度
  -> 观察线上指标和失败样本
  -> 全量发布或回滚
```

### 3.2 设计原则

| 原则 | 说明 |
| --- | --- |
| 版本不可变 | 已发布版本的 Prompt 内容和检索参数不允许原地修改，只能创建新版本。 |
| 激活指针可变 | `active`、`canary`、`archived` 等状态通过指针或状态流转切换。 |
| 请求内配置稳定 | 同一次请求解析出的配置快照不可在中途变化。 |
| 灰度可复现 | 百分比灰度基于稳定 hash，避免同一用户同一问题在版本间来回跳。 |
| 默认可回退 | 配置表异常时回退到文件 Prompt 和代码默认参数。 |
| 发布有证据 | 发布前建议绑定 Plan 1 的评测报告和关键指标 delta。 |

## 4. 核心对象模型

### 4.1 对象关系

```text
tenant
  -> kb
      -> prompt_family
          -> prompt_version
      -> retrieval_profile
      -> release_rule
          -> prompt bindings
          -> retrieval profile binding
          -> canary rule
```

核心对象说明：

| 对象 | 说明 |
| --- | --- |
| `prompt_family` | Prompt 逻辑名称，例如 `answer_out`、`hyde_prompt`、`query_understanding`。 |
| `prompt_version` | 某个 Prompt 的不可变内容版本。 |
| `retrieval_profile` | 一整套检索参数版本，例如是否启用 HyDE、RRF 权重、rerank top_k。 |
| `release_rule` | 配置匹配规则，决定某类请求使用哪些 Prompt 和检索策略。 |
| `query_config_snapshot` | 单次查询命中的配置快照，写入 State、事件和历史明细。 |

### 4.2 Prompt family 范围

第一阶段建议纳入以下 Prompt：

| Prompt family | 当前文件 | 使用位置 | 治理优先级 |
| --- | --- | --- | --- |
| `answer_out` | `prompts/answer_out.prompt` | `node_answer_output` | P0 |
| `hyde_prompt` | `prompts/hyde_prompt.prompt` | `node_search_embedding_hyde` | P0 |
| `query_understanding` | `prompts/query_understanding.prompt` | `query_understanding_utils` | P1 |
| `rewritten_query_and_itemnames` | `prompts/rewritten_query_and_itemnames.prompt` | `node_item_name_confirm` | P1 |

P0 先治理直接影响回答质量和检索召回的 `answer_out`、`hyde_prompt`；导入侧 Prompt 可在后续阶段复用同一版本模型。

## 6. 状态流转设计

### 6.1 Prompt version 状态

| 状态 | 含义 | 是否可查询命中 | 允许操作 |
| --- | --- | --- | --- |
| `draft` | 草稿，未进入线上 | 否 | 更新内容、绑定评测、提交灰度 |
| `canary` | 灰度版本 | 是，需命中灰度规则 | 全量发布、回滚、禁用 |
| `active` | 默认线上版本 | 是 | 归档、回滚到旧版 |
| `archived` | 历史版本 | 否 | 作为回滚目标恢复为 active |
| `disabled` | 禁用版本 | 否 | 仅审计保留 |

状态流转：

```text
draft
  -> canary
  -> active
  -> archived

canary
  -> archived

archived
  -> active

draft
  -> disabled
```

### 6.2 Retrieval profile 状态

`retrieval_profile` 状态与 Prompt version 保持一致，但发布时必须整体替换。禁止只把线上 active profile 的某个字段原地改掉。

### 6.3 Release rule 状态

| 状态 | 含义 |
| --- | --- |
| `draft` | 已创建但未生效。 |
| `active` | 参与线上匹配。 |
| `paused` | 暂停参与匹配，可再次恢复。 |
| `expired` | 已过期，不再参与匹配。 |
| `archived` | 历史规则，仅审计保留。 |

## 7. 配置匹配算法

### 7.1 输入

匹配算法输入来自 QueryGraphState 和 Query Understanding 结果：

```json
{
  "tenant_id": "default",
  "kb_id": "default",
  "user_id": "u001",
  "session_id": "s001",
  "query_type": "procedure",
  "original_query": "HAK 180 如何设置局部烫金区域？"
}
```

### 7.2 输出

```json
{
  "prompt_bindings": {
    "answer_out": {
      "version": "20260730_002",
      "content_sha256": "sha256:...",
      "model_params": {
        "model": "qwen3-32b",
        "temperature": 0.2
      }
    },
    "hyde_prompt": {
      "version": "20260730_001",
      "content_sha256": "sha256:..."
    }
  },
  "retrieval_profile": {
    "profile_id": "retrieval_default",
    "version": "20260730_002"
  },
  "match_reason": {
    "rule_id": "rule_answer_procedure_v2",
    "priority": 100,
    "matched_by": ["tenant_id", "kb_id", "query_type", "percent"],
    "hash_bucket": 17
  },
  "fallback_used": false
}
```

### 7.3 匹配优先级

按以下顺序匹配：

1. 精确 `tenant_id + kb_id + query_type + user_id/session_id` 规则。
2. 精确 `tenant_id + kb_id + query_type + percent` 规则。
3. 精确 `tenant_id + kb_id` 默认规则。
4. `tenant_id + default kb` 默认规则。
5. `default tenant + default kb` 全局默认规则。
6. 文件 Prompt 和代码默认检索参数 fallback。

### 7.4 百分比灰度

灰度桶使用稳定 hash：

```text
bucket = sha256(tenant_id + kb_id + hash_key_value + rule_id) % 100
hit = bucket < percent
```

设计要求：

- 同一用户在同一规则下稳定命中或不命中。
- 每次请求记录 `hash_bucket` 和 `rule_id`，便于问题复现。
- 当 `user_id=anonymous` 时，优先使用 `session_id` 作为 hash key。
- 当 `percent=0` 时规则不命中；当 `percent=100` 时跳过 hash 判断。

### 7.5 伪代码

```python
def resolve_query_config(scope, query_type):
    """解析本次查询命中的 Prompt 和检索策略配置。

    Args:
        scope: 查询租户、知识库、用户和会话范围。
        query_type: Query Understanding 输出的问题类型。

    Returns:
        单次查询可复现的配置快照。

    Raises:
        ConfigResolveError: 配置表存在但绑定资源缺失，且 fallback 不可用。
    """
    # 中文注释：按优先级从高到低查找规则，保证更精确的租户/知识库/问题类型配置优先生效。
    rules = load_active_rules(scope.tenant_id, scope.kb_id)
    matched_rule = first_rule_matched_by_priority(rules, scope, query_type)

    if matched_rule:
        return build_snapshot_from_rule(matched_rule)

    # 中文注释：配置系统异常或没有命中时回退到现有文件 Prompt 和代码默认参数，保证旧链路可用。
    return build_snapshot_from_file_prompts_and_defaults()
```

后续实现时，新增或修改的模块、公开函数、类应按项目要求补充 Google Style Docstring；匹配、灰度和 LangGraph State 更新等复杂逻辑需要增加中文注释。

## 8. LangGraph 接入设计

### 8.1 QueryGraphState 扩展

建议在 `app/query_process/agent/state.py` 中增加以下字段：

```python
class QueryGraphState(TypedDict):
    """定义查询流程中流转的数据结构。"""

    query_type: str
    query_config: dict
    prompt_versions: dict
    retrieval_profile_id: str
    retrieval_profile_version: str
    config_match_reason: dict
```

默认值：

```python
{
    "query_type": "unknown",
    "query_config": {},
    "prompt_versions": {},
    "retrieval_profile_id": "fallback_default",
    "retrieval_profile_version": "fallback",
    "config_match_reason": {"fallback_used": True}
}
```

### 8.2 新增配置解析节点

建议新增节点：

```text
node_resolve_query_config
```

接入位置：

```text
node_item_name_confirm
  -> node_resolve_query_config
  -> node_search_embedding
  -> node_search_embedding_hyde
  -> node_web_search_mcp
  -> node_rrf
  -> node_rerank
  -> node_answer_output
```

如果 `node_item_name_confirm` 已提前产生拒答或澄清答案，仍可以走 `node_answer_output`，但需要在回答事件中记录 fallback 配置，保证可观测字段完整。

### 8.3 节点读取规则

| 节点 | 读取配置 | 第一阶段改造方式 |
| --- | --- | --- |
| `node_search_embedding` | `retrieval_profile.embedding` | 将 top_k、ranker_weights、norm_score 从 profile 读取；缺省用当前值。 |
| `node_search_embedding_hyde` | `retrieval_profile.hyde`、`prompt_bindings.hyde_prompt` | 支持关闭 HyDE；Prompt 优先从配置快照读取。 |
| `node_web_search_mcp` | `retrieval_profile.web_search` | 支持按 profile 和 query_type 控制是否启用。 |
| `node_rrf` | `retrieval_profile.rrf` | top_k、k、source_weights 从 profile 读取。 |
| `node_rerank` | `retrieval_profile.rerank` | max_top_k、min_top_k、gap_ratio、gap_abs 从 profile 读取。 |
| `node_answer_output` | `prompt_bindings.answer_out`、`context`、`model_params` | Prompt 和上下文长度从配置快照读取。 |

### 8.4 Prompt 加载兼容

建议保留现有 `load_prompt(name, **kwargs)` 行为，并新增一个配置优先的包装函数：

```python
def load_prompt_for_query(state, prompt_id, **kwargs):
    """加载本次查询应使用的 Prompt 并渲染变量。

    Args:
        state: 查询 LangGraph State。
        prompt_id: Prompt 逻辑名称。
        **kwargs: Prompt 模板变量。

    Returns:
        渲染后的 Prompt 文本。

    Raises:
        FileNotFoundError: 配置和文件 fallback 都找不到 Prompt。
    """
```

加载顺序：

1. 从 `state["query_config"]["prompt_bindings"][prompt_id]["content"]` 读取。
2. 如果配置缺失，从 `prompts/{prompt_id}.prompt` 读取。
3. 渲染变量前校验变量白名单，避免发布了缺少占位符的 Prompt。
4. 返回 Prompt 文本，同时在 State 记录 `prompt_versions[prompt_id]`。

### 8.5 模型参数兼容

当前 `get_llm_client()` 主要从环境配置获取模型客户端。第一阶段建议只把模型参数写入配置快照和观测事件，不立即支持每个请求动态切换底层模型；第二阶段再增加：

```python
get_llm_client(model_params: dict | None = None)
```

渐进策略：

| 阶段 | 行为 |
| --- | --- |
| P0 | Prompt 版本可切换，模型仍使用默认环境配置。 |
| P1 | 支持 temperature、top_p、max_tokens 等生成参数。 |
| P2 | 支持按 Prompt version 或 release rule 切换模型名称。 |

## 10. 发布与回滚流程

### 10.1 Prompt 发布流程

```text
1. 创建 Prompt 草稿版本
2. 校验变量完整性和模板可渲染
3. 运行离线评测
4. 绑定评测报告和指标摘要
5. 创建 canary release rule
6. 激活灰度规则
7. 观察线上质量、错误率、延迟和用户反馈
8. 将灰度规则 percent 提升到 100 或创建默认 active 规则
9. 将旧版本归档
```

### 10.2 Retrieval profile 发布流程

```text
1. 复制当前 active profile 作为草稿
2. 修改 top_k、RRF、Rerank、HyDE、Web Search、Evidence Gate 参数
3. 使用 Plan 1 评测集运行 baseline 对比
4. 确认 Recall@K、MRR、answer correctness、citation precision 未明显下降
5. 创建灰度规则
6. 激活灰度并记录 match_reason
7. 全量发布或回滚
```

### 10.3 回滚流程

回滚不修改历史版本内容，只切换发布规则或 active 指针：

```text
1. 选择上一稳定版本或上一稳定 release rule
2. 创建 rollback audit log
3. 暂停当前 canary/active 规则
4. 激活旧版本规则
5. 清理本地配置缓存
6. 验证新请求命中旧版本
7. 记录回滚原因和关联故障事件
```

回滚验收：

- 新请求的 `query_config_snapshot` 中 `prompt_version` 和 `retrieval_profile_version` 已切回旧值。
- 观测事件能看到 `action=rollback` 的审计记录。
- 离线评测可用旧版本 profile 重新运行。

## 11. 评测报告绑定

### 11.1 绑定对象

评测报告可以绑定到：

- 单个 `prompt_version`。
- 单个 `retrieval_profile`。
- 单条 `release_rule`。

如果一次发布同时包含 Prompt 和检索策略变化，建议在 `release_rule` 上绑定综合评测报告，在具体版本上绑定单项实验报告。

### 11.2 关键指标

发布前建议至少记录：

| 指标 | Prompt 发布关注 | Retrieval profile 发布关注 |
| --- | --- | --- |
| `pass_rate` | 是 | 是 |
| `recall_at_5` | 间接关注 | 是 |
| `mrr_at_5` | 间接关注 | 是 |
| `answer_correctness_avg` | 是 | 是 |
| `faithfulness_avg` | 是 | 是 |
| `citation_precision` | 是 | 是 |
| `threshold_violations` | 是 | 是 |
| `newly_failed_cases` | 是 | 是 |

### 11.3 门禁建议

第一阶段只做记录和告警，不阻断发布；后续接入自动门禁时可以采用：

```text
核心样本 pass_rate 不低于 baseline - 2%
recall_at_5 不低于 baseline - 1%
faithfulness_avg 不低于 4.0
newly_failed_cases 中 P0 样本数量为 0
```

- release rule ID 和匹配原因。
- Rerank 输入输出数量和 top score。

回放时默认使用快照中的配置版本；如果版本已归档，仍可按不可变版本内容恢复当时行为。

## 13. 缓存与一致性

### 13.1 配置缓存

查询侧可以增加进程内 TTL 缓存，降低每次请求访问 MongoDB 的成本：

| 缓存对象 | 建议 TTL | 失效方式 |
| --- | --- | --- |
| active release rules | 30 秒 | 管理接口激活、暂停、回滚后主动清理。 |
| prompt version content | 5 分钟 | 版本不可变，可长缓存。 |
| retrieval profile | 5 分钟 | 版本不可变，可长缓存。 |

### 13.2 一致性策略

- 发布和回滚后，管理接口必须调用配置缓存失效。
- 即使某个进程未及时失效，TTL 到期后也会收敛。
- 请求开始时生成配置快照，请求执行中不再重新读取配置，避免半路切换。

## 14. 安全与权限

第一阶段最小权限控制：

- 查询接口只能读取 active/canary 命中的配置，不能提交任意 Prompt。
- 管理接口必须要求 `operator_id`，后续接 RBAC 时区分 admin/editor/viewer。
- 只有 admin/editor 可创建草稿，只有 admin 可激活、暂停、回滚。
- Prompt 内容和评测报告可审计，敏感业务信息不进入 Prometheus label。
- 如果 Prompt 内容来源于外部复制，发布前必须通过变量白名单和基础格式校验。

## 17. 验收标准

- 不修改代码即可切换 `answer_out` 和 `hyde_prompt` 版本。
- 配置表不可用时，查询能回退到 `prompts/*.prompt` 和当前默认检索参数。
- 每次回答都能在事件或快照中看到 `prompt_versions`、`retrieval_profile_id`、`retrieval_profile_version`、`release_rule_id` 和 `match_reason`。
- `retrieval_profile` 可以控制 HyDE、Web Search、RRF top_k、Rerank top_k 和断崖阈值。
- 新 Prompt 或检索策略可以按 `tenant_id`、`kb_id`、`query_type` 或百分比灰度。
- 灰度命中对同一用户稳定，可通过 `hash_bucket` 复现。
- 回滚后新请求能命中上一稳定版本，且审计日志记录回滚原因。
- Prompt 或 retrieval profile 发布前可以绑定 Plan 1 评测报告。

## 18. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 配置解析失败影响线上查询 | 保留文件 Prompt 和代码默认参数 fallback，并记录 `fallback_used=true`。 |
| 灰度命中不稳定导致问题难复现 | 使用稳定 hash，并记录 `rule_id`、`hash_key`、`hash_bucket`。 |
| 参数组合过多难治理 | 只允许通过 `retrieval_profile` 整体发布，不支持线上零散参数覆盖。 |
| Prompt 变量缺失导致运行时报错 | 创建草稿和激活前做模板变量校验。 |
| 发布版本缺少效果依据 | 强制记录或提示绑定评测报告，后续接自动门禁。 |
| 版本信息进入指标造成高基数 | 版本明细写事件和审计日志，Prometheus 只用低基数标签。 |
| 动态模型切换引入不稳定 | P0 只记录模型参数，P1/P2 再逐步支持请求级模型参数。 |

## 19. 推荐默认配置

第一阶段初始化全局默认版本：

```text
tenant_id = default
kb_id = default
prompt_versions:
  answer_out = prompts/answer_out.prompt 导入为 20260730_001
  hyde_prompt = prompts/hyde_prompt.prompt 导入为 20260730_001
retrieval_profile:
  profile_id = retrieval_default
  version = 20260730_001
  embedding.enabled = true
  hyde.enabled = true
  web_search.enabled = false
  rrf.top_k = 5
  rerank.max_top_k = 10
  context.max_context_chars = 12000
release_rule:
  rule_id = rule_default_active
  priority = 0
  percent = 100
```

这样可以先把当前行为固化为一个可追踪 baseline，再逐步发布新 Prompt 和新检索策略。

# kbase-rag 监控与告警优化方案

## 1. 背景

根据 `OBSERVABILITY_DESIGN.md` 的设计目标，项目第三阶段已经完成了事件持久化、节点快照、回放 API、LangGraph checkpoint 等能力。当前系统已经具备从单次请求定位到节点、事件、快照的诊断基础，但从稳定性视角看，监控和告警还需要从“能排查”升级为“能提前发现、能分级叫醒、能指导处置”。

本文基于当前代码与部署配置，针对查询链路、导入链路、LLM、Milvus、MongoDB、SSE、观测系统自身和告警路由提出优化方案。

### 2.2 主要短板

| 短板 | 稳定性影响 | 优先级 |
| --- | --- | --- |
| 缺少 Alertmanager 和 Prometheus rule 文件 | 指标已有，但无法形成标准告警闭环。 | P0 |
| LLM Prometheus 指标未落地 | Langfuse 能看调用细节，但无法用统一告警规则监控错误率、耗时、token、降级。 | P0 |
| 熔断状态没有导出到指标 | 已有进程内熔断，但 Grafana/Prometheus 不知道电路状态。 | P0 |

| SSE 连接数、断连、队列积压不可见 | 流式查询体验劣化时难以及时发现。 | P1 |

| Dashboard 只有总览雏形 | 当前面板覆盖吞吐和部分耗时，缺少错误率、SLO、依赖、告警态和自监控。 | P1 |
| 告警分级和抑制策略不清晰 | 容易出现误报、刷屏或关键故障无人响应。 | P1 |
| 缺少观测体系自监控 | Collector/Promtail/Loki/Tempo/Grafana 出问题时可能先失明。 | P1 |

## 3. 稳定性目标

建议先建立以下 SLO，后续根据真实流量校准。

| 链路 | SLI | 初始目标 | 说明 |
| --- | --- | --- | --- |
| 查询可用性 | `ok + degraded` / total | 99.0% | 熔断兜底返回计为 degraded，不计为完全失败。 |
| 查询延迟 | P95 workflow duration | < 15s | 同步查询和流式查询分别看。 |
| 首 token 延迟 | P95 time to first delta | < 5s | 需新增 SSE 首包指标。 |
| 导入可用性 | completed / total | 98.0% | 导入链路受文件质量影响，应按文件类型拆分。 |
| 导入耗时 | P95 import duration | PDF < 5min，MD < 2min | 初始阈值可宽松，按历史数据收敛。 |
| LLM 可用性 | successful LLM calls / total | 99.0% | 按模型和 json_mode 拆分。 |
| Milvus 可用性 | successful operations / total | 99.5% | 查询链路强依赖。 |
| 事件可用性 | Mongo event write success / total | 99.9% | 低于目标会影响事后排障。 |
| 观测栈可用性 | collector/promtail/loki/tempo up | 99.9% | 观测系统本身必须被监控。 |

## 4. 指标优化

### 4.1 指标设计原则

1. 标签必须低基数：禁止把 `session_id`、`task_id`、`trace_id`、用户问题、文件名、chunk 文本作为 metric label。
2. 状态标签统一为 `ok`、`error`、`degraded`、`timeout`、`cancelled`。
3. 外部依赖统一使用 `dependency`、`operation`、`status` 标签。
4. 告警指标必须覆盖 RED：Rate、Errors、Duration。
5. 长任务必须补充队列、并发、年龄指标，避免只在失败后才发现。

### 4.2 需要新增的核心指标

| 指标 | 类型 | 标签 | 触发位置 | 用途 |
| --- | --- | --- | --- | --- |
| `rag_llm_requests_total` | Counter | `model`, `status`, `json_mode`, `fallback` | LLM 调用包装层 | LLM 错误率、降级率。 |
| `rag_llm_duration_seconds` | Histogram | `model`, `status`, `json_mode`, `fallback` | LLM 调用包装层 | LLM P95/P99。 |
| `rag_llm_tokens_total` | Counter | `model`, `type` | LLM 回调或 Langfuse 回填 | token 消耗趋势和异常消耗。 |
| `rag_llm_stream_first_token_seconds` | Histogram | `model`, `status` | 流式生成首个 delta | 首包延迟。 |
| `rag_rerank_duration_seconds` | Histogram | `model`, `status` | reranker 工具 | rerank 慢调用。 |
| `rag_rerank_docs_total` | Histogram | `stage` | rerank 节点 | rerank 输入/输出分布。 |
| `rag_retrieval_docs_total` | Histogram | `source` | embedding/hyde/web/rrf 节点 | 召回不足和搜索退化。 |
| `rag_mongo_operations_total` | Counter | `operation`, `collection`, `status` | Mongo 历史与事件存储 | Mongo 错误率。 |
| `rag_mongo_operation_duration_seconds` | Histogram | `operation`, `collection`, `status` | Mongo 历史与事件存储 | Mongo 慢查询。 |
| `rag_minio_operations_total` | Counter | `operation`, `bucket`, `status` | 快照保存/读取 | 快照故障。 |
| `rag_minio_operation_duration_seconds` | Histogram | `operation`, `bucket`, `status` | 快照保存/读取 | MinIO 延迟。 |
| `rag_event_store_writes_total` | Counter | `backend`, `status` | `events.py` | Mongo 写入和 JSONL 降级。 |
| `rag_event_store_fallback_total` | Counter | `reason` | `events.py` | 中心事件存储不可用告警。 |
| `rag_snapshot_total` | Counter | `backend`, `graph`, `kind`, `status` | `snapshots.py` | 快照保存是否正常。 |
| `rag_replay_total` | Counter | `graph`, `mode`, `status` | `replay.py` | 回放可用性和失败率。 |
| `rag_sse_connections` | UpDownCounter/Gauge | `state` | `sse_generator` | 当前连接、断连、异常断连。 |
| `rag_sse_queue_depth` | Histogram/Gauge | 无或 `bucket` | `push_to_session` | 队列积压和客户端消费慢。 |
| `rag_task_inflight` | UpDownCounter/Gauge | `graph` | workflow 开始/结束 | 后台任务并发。 |
| `rag_task_age_seconds` | Histogram | `graph`, `status` | 状态查询或定时扫描 | 卡住任务发现。 |
| `rag_circuit_state` | Gauge | `name`, `state` | `ConsecutiveFailureMonitor` | 熔断开路告警。 |
| `rag_consecutive_failures` | Gauge | `name` | `ConsecutiveFailureMonitor` | 连续失败趋势。 |
| `rag_dependency_health` | Gauge | `dependency` | `/health/ready` 或探测任务 | 依赖健康。 |

### 4.3 当前指标补齐建议

1. 在 `app/observability/metrics.py` 增加统一函数：
   - `record_llm_call(...)`
   - `record_llm_tokens(...)`
   - `record_rerank(...)`
   - `record_retrieval_docs(...)`
   - `record_mongo_operation(...)`
   - `record_minio_operation(...)`
   - `record_event_store_write(...)`
   - `record_snapshot(...)`
   - `record_replay(...)`
   - `record_circuit_state(...)`
   - `record_sse_connection(...)`
   - `record_task_inflight(...)`
2. 在 `app/utils/alert_utils.py` 的 `record_success`、`record_failure`、`state` 状态转换点同步更新 `rag_circuit_state` 和 `rag_consecutive_failures`。
3. 在 `app/observability/events.py` 的 Mongo 成功、Mongo 失败、JSONL 成功、JSONL 失败分支记录 event store 指标。
4. 在 `app/observability/snapshots.py` 的 MinIO 和本地文件分支记录 snapshot 指标。
5. 在 LLM 调用处增加业务包装器，不只依赖 Langfuse。Langfuse 保留细节，Prometheus 负责统一告警。
6. 在 `app/utils/sse_utils.py` 中记录连接建立、正常关闭、客户端断开、异常结束、当前队列数量和队列深度。

## 5. 健康检查优化

### 5.1 拆分 liveness 和 readiness

当前查询服务有 `/health`，建议两个服务都补齐：

| 接口 | 语义 | 检查内容 | 用途 |
| --- | --- | --- | --- |
| `/health/live` | 进程存活 | 只返回进程是否能响应 | 容器/进程重启判断。 |
| `/health/ready` | 服务可接流量 | MongoDB、Milvus、LLM base_url、Redis、Checkpoint Postgres、MinIO、OTel Collector 可达性 | 上线、负载均衡摘流。 |
| `/health/observability` | 观测能力 | event store、snapshot store、checkpoint backend、OTLP exporter 配置状态 | 防止排障能力静默失效。 |

### 5.2 readiness 返回格式

```json
{
  "status": "ok",
  "service": "query",
  "checks": {
    "mongo": {"status": "ok", "duration_ms": 12},
    "milvus": {"status": "ok", "duration_ms": 31},
    "llm": {"status": "ok", "duration_ms": 120},
    "event_store": {"status": "ok", "backend": "mongo"},
    "snapshot_store": {"status": "degraded", "backend": "local"}
  }
}
```

readiness 中 `status=degraded` 不一定拒绝流量，但必须进入告警和 Dashboard。

## 6. 告警分级策略

### 6.1 级别定义

| 级别 | 触发条件 | 响应目标 | 通知方式 |
| --- | --- | --- | --- |
| critical | 用户请求大面积失败、核心依赖不可用、熔断打开、观测主链路失明 | 15 分钟内处理 | 电话/IM 强提醒 + 邮件。 |
| warning | 错误率、耗时、资源、降级趋势异常但仍可服务 | 工作时间 30 分钟内处理 | IM + 邮件。 |
| info | 低风险变化、容量趋势、自动恢复通知 | 观察即可 | IM 低优先级。 |

### 6.2 抑制和收敛

1. 当 `ServiceDown` 触发时，抑制同服务的 HTTP 错误率、节点错误、LLM 错误等派生告警。
2. 当 `ObservabilityPipelineDown` 触发时，抑制 Loki/Tempo 查询失败类告警。
3. 同一 `alertname + service + severity` 在 30 分钟内聚合一次，避免刷屏。
4. 所有 warning 级别设置 `for: 5m` 或更长，避免瞬时抖动。
5. critical 级别仍需 `for: 2m`，防止单点采样误判。

## 7. Prometheus 告警规则建议

建议新增 `deploy/observability/rules/kbase-rag-alerts.yml`，并在 `prometheus.yml` 中配置 `rule_files`。

### 7.1 服务和观测栈

```yaml
groups:
  - name: kbase-rag-service
    rules:
      - alert: DatasetRagMetricsMissing
        expr: absent(rag_http_requests_total)
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: kbase-rag 业务指标缺失
          description: 5 分钟内未采集到 rag_http_requests_total，可能是应用、OTel Collector 或 Prometheus 链路异常。

      - alert: OtelCollectorDown
        expr: up{job="otel-collector"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: OpenTelemetry Collector 不可用
          description: Prometheus 无法抓取 otel-collector:8889。
```

### 7.2 查询链路

```yaml
  - name: kbase-rag-query
    rules:
      - alert: QueryHighErrorRate
        expr: |
          (
            sum(rate(rag_query_total{status="error"}[5m]))
            /
            clamp_min(sum(rate(rag_query_total[5m])), 0.001)
          ) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: 查询错误率过高
          description: 最近 5 分钟查询错误率超过 5%。

      - alert: QueryCriticalErrorRate
        expr: |
          (
            sum(rate(rag_query_total{status="error"}[5m]))
            /
            clamp_min(sum(rate(rag_query_total[5m])), 0.001)
          ) > 0.20
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: 查询错误率严重过高
          description: 最近 5 分钟查询错误率超过 20%，需要立即处理。

      - alert: QueryP95TooHigh
        expr: |
          histogram_quantile(
            0.95,
            sum(rate(rag_query_duration_seconds_bucket[5m])) by (le, is_stream)
          ) > 15
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: 查询 P95 耗时过高
          description: 查询 workflow P95 超过 15 秒，按 is_stream 拆分排查。

      - alert: QueryNodeP95TooHigh
        expr: |
          histogram_quantile(
            0.95,
            sum(rate(rag_node_duration_seconds_bucket{graph="query"}[5m])) by (le, node_name)
          ) > 8
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: 查询节点 P95 耗时过高
          description: 某个查询 LangGraph 节点 P95 超过 8 秒。
```

## 8. Alertmanager 部署建议

### 8.1 Compose 补充

建议在 `deploy/observability/docker-compose.yml` 增加：

```yaml
  alertmanager:
    image: prom/alertmanager:v0.27.0
    command:
      - "--config.file=/etc/alertmanager/alertmanager.yml"
      - "--storage.path=/alertmanager"
    volumes:
      - ./alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro
      - alertmanager-data:/alertmanager
    ports:
      - "19093:9093"
```

Prometheus 增加：

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]

rule_files:
  - /etc/prometheus/rules/*.yml
```

### 8.2 路由建议

```yaml
route:
  receiver: default
  group_by: ["alertname", "service", "severity"]
  group_wait: 30s
  group_interval: 10m
  repeat_interval: 2h
  routes:
    - matchers:
        - severity="critical"
      receiver: critical
      repeat_interval: 30m
    - matchers:
        - severity="warning"
      receiver: warning

receivers:
  - name: default
    webhook_configs:
      - url: http://host.docker.internal:9000/alerts/default
  - name: critical
    webhook_configs:
      - url: http://host.docker.internal:9000/alerts/critical
  - name: warning
    webhook_configs:
      - url: http://host.docker.internal:9000/alerts/warning

inhibit_rules:
  - source_matchers:
      - alertname="OtelCollectorDown"
    target_matchers:
      - alertname!="OtelCollectorDown"
    equal: ["service"]
```

如果暂时没有统一告警 webhook，可以先接邮件、企业微信、飞书或 Server 酱，但建议最终统一到 Alertmanager，`app/utils/alert_utils.py` 的进程内告警作为近实时兜底，不作为唯一告警来源。

## 11. 稳定性专题优化

### 11.1 LLM 监控

建议增加 `app/lm/observed_llm.py` 或在 `lm_utils.py` 中提供统一调用函数，确保所有模型调用都经过同一层：

1. 记录请求开始和结束。
2. 区分初始化失败、请求超时、限流、模型返回格式错误、解析错误。
3. 记录 fallback 是否发生。
4. 记录 json_mode。
5. 尽量从 response metadata 提取 token；提取不到时记录 `unknown`，不要阻塞主流程。
6. 将 LLM 错误传递给 `llm_failure_monitor`，并同步更新 Prometheus 熔断指标。

### 11.2 SSE 监控

建议记录以下事件和指标：

1. `sse.connected`：客户端连接建立。
2. `sse.disconnected`：客户端主动断开。
3. `sse.generator.failed`：生成器异常退出。
4. `sse.queue_missing`：推送时找不到队列。
5. `sse.first_delta`：首个 delta 发送。
6. `sse.final_sent`：最终结果发送。

告警关注：

1. `queue_missing` 在 5 分钟内大于 0，说明后台任务和前端连接生命周期不一致。
2. 首 token P95 超过 5 秒，说明模型或前置检索慢。
3. 异常断连超过基线 3 倍，说明前端、网关或服务端流式响应不稳定。

### 11.3 事件和快照自监控

第三阶段完成后，事件和快照是故障复现的关键能力，必须纳入稳定性目标：

1. Mongo event write 失败时记录 `rag_event_store_fallback_total{reason="mongo_write_failed"}`。
2. JSONL fallback 写入失败时触发 critical，因为此时事件完全丢失。
3. MinIO 快照失败但本地 fallback 成功时 warning。
4. MinIO 和本地都失败时 critical。
5. 快照保存耗时 P95 超过 1 秒时 warning，避免节点包装器拖慢主流程。

### 11.4 Checkpoint 监控

当前 `checkpoints.py` 支持 memory/postgres，生产应强制 postgres。建议：

1. readiness 中暴露 checkpoint backend 和 persistent 状态。
2. 指标 `rag_checkpoint_backend{backend="postgres"} 1`。
3. 指标 `rag_checkpoint_operations_total{operation,status}`。
4. 指标 `rag_checkpoint_operation_duration_seconds{operation,status}`。
5. 生产环境如果 backend 为 memory，直接 critical 告警。

### 11.5 任务卡住检测

导入和流式查询都可能进入 background task 后卡住。建议增加定时扫描或状态更新时计算：

1. `processing` 状态超过 10 分钟的查询任务告警。
2. `processing` 状态超过 30 分钟的导入任务告警。
3. running node 超过节点历史 P99 的 2 倍告警。
4. 同一个 task 长时间没有 `task.status_changed` 或 `node.completed` 事件告警。

## 12. Runbook 建议

每条 critical 告警都应包含 runbook 链接。初始可以写在本文中，后续拆分为独立文档。

### 12.1 查询错误率过高

1. 打开 Grafana 总览，看 `QueryHighErrorRate` 是否伴随 `LlmHighErrorRate`、`MilvusHighErrorRate`。
2. 按 `rag_node_duration_seconds{status="error"}` 找到 Top 错误节点。
3. 在 Loki 中按错误节点过滤日志。
4. 从错误日志拿 `trace_id` 或 `session_id`，打开 `/debug/sessions/{session_id}/timeline`。
5. 如果是节点确定性失败，使用 `/debug/replay/latest-failed` 或 `/debug/replay/node` 验证。
6. 如果是外部依赖失败，确认是否需要临时降级、切备用模型或暂停导入。

### 12.2 LLM 错误率过高

1. 看是否集中在某个 `model` 或 `json_mode`。
2. 查看 `rag_circuit_state{name="llm"}` 是否 open。
3. 检查供应商返回：超时、429、5xx、格式错误分开处理。
4. 如果备用模型可用，确认 fallback 流量是否正常。
5. 如果 prompt/token 暴涨，检查最近导入文档或 query rewrite 是否异常。

### 12.3 Milvus 慢查询或错误

1. 按 `operation`、`collection` 定位。
2. 查看是否与 embedding batch 或导入入库高峰重叠。
3. 检查 collection 索引、数据量、过滤表达式和 limit。
4. 使用 trace 定位上游节点是否传入过大的候选集。
5. 必要时限制并发导入或降低查询 top_k。

### 12.4 事件存储降级

1. 检查 MongoDB 连接、认证、磁盘和索引。
2. 查看本地 `logs/observability_events.jsonl` 是否持续增长。
3. 恢复 Mongo 后执行补偿导入脚本，将 JSONL 事件回灌 Mongo。
4. 确认 `/debug/sessions/{session_id}/timeline` 可以查到新事件。

### 12.5 快照保存失败

1. 检查 MinIO 配置、bucket、认证和磁盘。
2. 查看是否降级到 `logs/observability_snapshots`。
3. 如果本地也失败，优先恢复磁盘写入能力。
4. 临时将 `OBSERVABILITY_SNAPSHOT_LEVEL=off` 可降低主流程压力，但需要同步告警说明回放能力受限。

### 12.6 观测栈或指标缺失

1. 先看 Grafana 总览中的 `Firing Alerts` 和 `Dependency and Stack Health`。
2. 打开 `http://localhost:19090/targets`，确认 `otel-collector`、`prometheus`、`loki`、`tempo`、`grafana`、`alertmanager`、`promtail` 目标是否都为 `UP`。
3. 如果 `rag_http_requests_total` 消失，优先检查应用进程、OTel Collector 和 Prometheus 的抓取链路。
4. 如果 `OtelCollectorDown` 触发，先恢复 Collector，再看其他派生告警是否自动收敛。
5. 任何事件都可以用 `trace_id` 或 `session_id` 打开 `/debug/traces/{trace_id}/timeline`、`/debug/sessions/{session_id}/timeline`，再进入 `/debug/replay/latest-failed` 做复现。

### 12.7 查询延迟和节点排查

1. 打开 `Dataset RAG Query` dashboard，先看查询吞吐、错误率和 SSE 首 token。
2. 按 `rag_node_duration_seconds{graph="query"}` 找到最慢节点，再去 Loki 按 `trace_id` 或 `session_id` 过滤日志。
3. 从 `/debug/sessions/{session_id}/timeline` 确认节点顺序和事件摘要。
4. 如果是确定性节点失败，优先用 `/debug/replay/node` 或 `/debug/replay/failed` 复现。
5. 如果是外部依赖慢，结合 `Dataset RAG Dependencies` 面板查看 LLM、Milvus、MongoDB 的错误率和 P95。

### 12.8 导入链路异常

1. 打开 `Dataset RAG Import` dashboard，看导入吞吐、失败率和节点 P95。
2. 在 `/debug/tasks/{task_id}/timeline` 中确认卡住的节点和最后一条成功事件。
3. 按 `task_id` 去 Loki 查询对应日志，确认是不是文件格式、切块、商品识别或入库节点失败。
4. 如果需要复现，优先用 `mock_external` 回放；只有在隔离环境中才启用 `live_external`。

### 12.9 告警到 trace / timeline / replay 的统一路径

1. 告警先看 `dashboard_url`，再看告警标签里的 `service`、`severity`、`alertname`。
2. 若告警消息里带 `trace_id`，直接打开 `/debug/traces/{trace_id}/timeline`。
3. 若只有 `session_id` 或 `task_id`，先打开对应 timeline，再从事件详情跳到快照和 checkpoint。
4. timeline 找到异常节点后，进入 `/debug/replay/latest-failed` 或 `/debug/replay/node`。
5. replay 结束后，对比 `/debug/snapshots/diff`，确认是上游输入变化还是节点逻辑变化。

### 12.10 合成探测失败

1. 打开 `Dataset RAG Observability` dashboard，确认 `rag_synthetic_probe_total` 是 `error` 还是 `degraded`。
2. 如果是 readiness 失败，优先查看 `/health/ready` 中 Mongo、Redis、Milvus、LLM、OTel 的具体 check。
3. 如果是 observability 失败，查看 `/health/observability` 中 event store、snapshot store、checkpoint backend 和 OTLP exporter。
4. 在 Loki 按 `event_type="synthetic.probe.completed"` 或 `synthetic` 标签查最近探测摘要。
5. 恢复依赖后确认 `SyntheticProbeFailed` resolved，并确认新的 synthetic 事件状态回到 `ok`。

### 12.11 任务卡住

1. 打开 `Dataset RAG Query` 或 `Dataset RAG Import` dashboard，看 `rag_task_age_seconds{status="processing"}`。
2. 在 timeline 中查 `task.stuck.detected` 事件，事件 summary 会包含 `task_id` 或 `session_id`、running 节点和 idle 秒数。
3. 查询任务打开 `/debug/sessions/{session_id}/timeline`，导入任务打开 `/debug/tasks/{task_id}/timeline`。
4. 如果最后事件停在某个节点，优先检查该节点依赖；必要时用 `/debug/replay/latest-failed` 或 `/debug/replay/node` 复现。
5. 如果任务实际已结束但状态未更新，检查 `update_task_status` 调用路径和 Redis/内存任务状态是否一致。

### 12.12 容量不足

1. 打开 `Dataset RAG Observability` dashboard，查看 `rag_capacity_headroom` 和 `rag_capacity_used_ratio`。
2. 如果 scope 是 `logs`，先清理或归档历史 JSONL 日志，并确认 Loki/Promtail 保留期。
3. 如果 scope 是 `output`，清理已完成导入任务的中间文件或调整文件保留策略。
4. 如果 Prometheus、Loki、Tempo、Mongo、MinIO、Postgres 容量不足，优先确认各组件的数据目录和 retention 配置。
5. 容量恢复后确认 `CapacityHeadroomLow` resolved，并保留至少 3 天以上增长余量。

## 13. 分阶段落地计划

### 阶段 A：告警闭环，1-2 天

1. 增加 Alertmanager 服务和配置。
2. Prometheus 增加 `rule_files` 和 Alertmanager target。
3. 新增 `kbase-rag-alerts.yml`，先覆盖查询、导入、Milvus、Collector、指标缺失。
4. Grafana 接入 Alertmanager。
5. 验证手动触发告警、恢复通知、抑制规则。

验收标准：

1. 停掉 OTel Collector 后 2-5 分钟内收到 critical 告警。
2. 模拟查询失败后能收到 QueryHighErrorRate。
3. 告警消息包含 service、severity、summary、dashboard 链接。

### 阶段 B：业务指标补齐，3-5 天

1. 补齐 LLM、rerank、retrieval、Mongo、MinIO、event store、snapshot、replay 指标。
2. 熔断状态和连续失败计数导出到 Prometheus。
3. SSE 连接、断连、首 token 和队列指标落地。
4. 增加 `/health/live`、`/health/ready`、`/health/observability`。

验收标准：

1. Grafana 能看到 LLM 错误率、耗时、fallback、token 趋势。
2. Mongo event store 降级时能收到 warning。
3. 熔断打开时 Prometheus 查询 `rag_circuit_state{state="open"}` 为 1。
4. SSE 客户端断开能在指标和事件中看到。

### 阶段 C：Dashboard 和 Runbook，2-4 天

1. 扩展总览 Dashboard。
2. 新增查询链路、导入链路、依赖、自监控 Dashboard。
3. 为每条 critical/warning 告警补充 runbook 链接。
4. 在 Debug 页面或文档中补充从告警到 trace/timeline/replay 的排障路径。

验收标准：

1. 值班人员可在 5 分钟内从告警定位到异常节点或依赖。
2. 任一错误 session 可通过 `trace_id` 或 `session_id` 找到日志、事件、快照。
3. Dashboard 不使用高基数字段作为标签过滤。

### 阶段 D：稳定性自动化，5-8 天

1. 增加合成探测：定时执行轻量查询、轻量导入或 dry-run 检查。
2. 增加任务卡住扫描。
3. 增加 JSONL fallback 回灌 Mongo 工具。
4. 增加容量告警：Prometheus、Loki、Tempo、Mongo、MinIO、Postgres 磁盘和保留期。
5. 将告警规则纳入测试或 CI 校验，防止 PromQL 语法错误。

当前落地：

1. `app/observability/automation.py` 在 query/import 服务启动时执行 readiness、observability 合成探测。
2. `app/utils/task_utils.py` 记录任务 `created_at`、`updated_at`、`graph`，并提供卡住任务扫描快照。
3. `app/observability/jsonl_backfill.py` 支持 JSONL fallback dry-run 和 `--write` 回灌 Mongo。
4. `rag_capacity_headroom`、`rag_capacity_used_ratio` 覆盖本地容量探测，可通过 `OBSERVABILITY_CAPACITY_PATHS` 指向 Prometheus、Loki、Tempo、Mongo、MinIO、Postgres 数据目录。
5. `deploy/observability/validate_prometheus_rules.py` 支持 promtool 校验，未安装 promtool 时执行结构校验。

验收标准：

1. 合成探测失败能在用户投诉前告警。
2. 卡住任务能被发现并给出 task/session ID 的后续排查入口。
3. 观测组件容量不足提前 3 天以上 warning。

## 15. 风险和注意事项

1. 不要把 `session_id`、`task_id`、`trace_id` 放入 metric label，否则 Prometheus 高基数会快速膨胀。
2. LLM token 和 prompt 内容不能直接进入日志或指标；指标只记录数量，内容继续按脱敏/摘要/快照策略处理。
3. 快照保存失败不能影响主流程，但必须告警，否则回放能力会静默失效。
4. 进程内连续失败告警在多实例部署时只能看到单实例状态，必须用 Prometheus 聚合告警作为主告警。
5. 本地 JSONL fallback 是短期兜底，不是长期事件存储；必须监控、告警、回灌。
6. live replay 可能调用外部依赖或产生副作用，生产默认保持 `OBSERVABILITY_REPLAY_ALLOW_LIVE=false`。
7. Dashboard 阈值上线初期应按历史数据每周校准，避免过度告警。

1. 增加 Alertmanager。
2. 增加 Prometheus rule file。
3. 告警覆盖查询错误率、查询 P95、导入失败率、Milvus 错误率、Collector down。

5. 熔断状态导出为 `rag_circuit_state`。

完成以上清单后，项目将具备从“请求失败”到“自动告警”再到“trace/log/event/snapshot/replay 联合定位”的稳定性闭环。
